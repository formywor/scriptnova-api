# Nebula API

Server-only source for the existing Vercel project. Upload the contents of this `api` directory to the API repository root. The main website remains a separate GitHub Pages repository. No secrets belong in either repository.

## Active public model: Nebula Ultra

The public catalog now exposes Nebula Ultra. Classic, V1, V1 Lite and V2.1 are disabled with `Currently in training`; older client selections route to Ultra. API replies and saved messages record the actual Ultra model identity.

Set server-only `NEBULA_ULTRA_API_KEY` and optionally `NEBULA_ULTRA_MODEL` (default `openai/gpt-oss-20b`). The key falls back to `GROQ_API_KEY`, then `NEBULA_REVIEW_GROQ_API_KEY`. No key is sent to the website. Missing configuration and upstream rate limits produce explicit unavailable/busy states.

Ultra uses Groq Chat Completions for writing, explanations, coding help and planning. It cannot browse or execute code. On explicit appearance requests it may return one allowlisted settings patch. Theme, font, size, spacing, accents, animation, starters and layout are supported. The browser validates the patch again, saves account preferences when signed in, and offers Undo. No generated HTML/CSS/JavaScript executes.

Training sharing and optional reviews retain their independent consent checks. Normal Ultra generation requires sending relevant chat context to Groq; the website discloses this separately. Model artifacts are excluded from this API bundle while experimental models are unavailable. `check:model` skips legacy artifact checks unless `NEBULA_VALIDATE_TRAINING_MODELS=true`.

## Accounts, storage, and contributions

Keep the existing Firebase server credentials, public Firebase app configuration, allowed origins, and stable random `NEBULA_RATE_LIMIT_SECRET` in Vercel. The rate-limit secret needs at least 32 characters. Firebase verifies ID tokens server-side. Account chats and preferences sync through the API; guest chats are temporary and have a shared-network question allowance. The supplied database rules deny browser database access. CORS is not authentication.

Sharing is on for new accounts and can be disabled in Settings. The server requires the account sharing preference, new-turn eligibility flag, versioned contribution flag, valid identifiers, and a fresh consent-generation check after generation. Set `NEBULA_TRAINING_ENABLED=false` to disable capture globally; otherwise consent-controlled capture is enabled. Imported older messages are excluded.

Only the latest consented message and reply become pending review records in private Firebase `nebulaTraining/v1`. Basic email/key redaction is not a comprehensive personal-data filter. Raw messages are not application logs. Public submissions and the model's own replies are never automatically accepted as factual teaching answers.

Captured account turns also produce a small private `nebulaLearning/v1` metadata index containing a topic, timestamp, and consent ownership references, with no chat text. The trainer-only `GET /api/nebula/research/curriculum` samples at most 100 owners, rechecks current account sharing and generation, uses the last seven days, and returns only four coarse topic counts rounded to multiples of five. It never returns text, IDs, names or replies. The sample rotates hourly. The evaluator token and browser-origin requests cannot read this feed.

The V5 GPU worker actually uses these counts to choose verified practice for at most one round in four. This influences weight updates through owned exercises; it does not instantly memorize a visitor's messages or train on unchecked answers. Small samples or an unavailable API feed fall back to the normal curriculum. Raw contributions remain pending for separate operator review. Account opt-outs exclude existing contributions from future topic requests. Deleting shared data tombstones both contribution stores and rotates the account generation. Deletion cannot undo completed training. Chat deletion and shared-data deletion are separate controls.

## Conversation experience and optional reviews

GET `/api/nebula/models` returns the fixed owned-model choices and feature availability, never private provider configuration. Clients select only allowlisted model IDs and Quick/Standard/Expanded generation budgets. Extended reasoning is explicitly unavailable. Account personalization, starter-question preferences, display settings and default model/length choices are validated and synchronized through account preferences. Owner instructions remain first; preferences are subordinate context, not a replacement for server rules.

Optional external answer review requires three private Vercel variables: `NEBULA_REVIEW_ENABLED=true`, `NEBULA_REVIEW_API_KEY`, and `NEBULA_REVIEW_MODEL` (a model available to that key). The current server adapter uses the Gemini generateContent API. The existing server-side `GEMINI_API_KEY` can be used as a key fallback. No provider key or model endpoint goes in website files. Deploy both API and website updates.

The public setting is **Allow third-party AI reviews**, directly below **Improve Nebula for everyone**. New accounts start with both settings on, disclosed in sign-in and settings. Either can be changed independently. Turning training sharing on enables reviews only if the user has never manually set a review preference. Existing manual opt-outs are retained. Existing accounts without explicit review consent remain off until enabled.

Reviews include the whole eligible conversation, redacted, excluding exchanges sent with review off, Classic, imported/unversioned answers and prior published checkpoint revisions. New server answers carry a checkpoint fingerprint and timestamp. About three fresh replies trigger a batch; rapid chats (five replies within five minutes) wait for eight fresh replies or ten idle minutes. Other chats flush after five idle minutes. The open website scans saved chats once a minute, including chats not currently open; checks resume on return. There is no closed-browser background scheduler. Server leases prevent duplicate calls across devices. A one-minute account cooldown, five-minute chat cooldown and ten-minute failure retry replace the old three-attempts/48-hour cap; provider failures defer quietly. Reviews over 120,000 serialized characters are skipped rather than silently truncated. Remote models should set NEBULA_MODEL_REVISION to a new identifier whenever their deployed weights change.

The provider sees dialogue only, never account profiles, memory or credentials. It reviews the dialogue as context and proposes a correction for the final answer. Results are attached to a pending contribution only when training sharing is also on and the contribution remains eligible. Review-only mode does not export training data. Opt-outs are checked before the call and before persistence; a call already sent cannot be recalled.

Reviews are stored privately alongside pending contributions. The private `model-data.mjs export` command includes proposed corrected answers and review provenance, but keeps every row pending for operator approval. Uncertain reviews do not replace the original answer. The existing consent-checked review/training pipeline can then use approved corrections. Neither public model weights nor Kaggle V5's fixed research dataset change automatically from these reviews. The V5 notebook still uses anonymous topic-guided verified practice. No automatic public promotion is added.

## Review provider routing

Reviews can use Groq and Gemini. Add `GROQ_API_KEY` (or the dedicated `NEBULA_REVIEW_GROQ_API_KEY`) in Vercel; `NEBULA_REVIEW_GROQ_MODEL` defaults to `openai/gpt-oss-20b`. Existing `NEBULA_REVIEW_API_KEY`/`GEMINI_API_KEY` and `NEBULA_REVIEW_MODEL` remain Gemini's configuration. Either provider alone is sufficient. `NEBULA_REVIEW_ENABLED=true` still gates all reviews. Keys and model configuration remain server-only.

First passes alternate between configured, healthy providers using a Firebase transaction. Confirmation prefers the other provider when healthy, with fallback to the working one. Valid uncertain/rejected verdicts are not failures and never trigger a search for an approving provider. HTTP errors, rate limits, timeouts and malformed output try the other provider immediately. Failures create a shared 1-minute cooldown, increasing up to 15 minutes for repeated failures; when it expires the provider becomes eligible for a probe. If only one is healthy, all new calls go there. If both are unavailable, reviews defer; ordinary chat continues. The cooldown survives Vercel cold starts through `nebulaReviewRouting/v1`.

Both transports use fixed HTTPS hosts, no redirects, 18-second request timeouts, a 24 KB streamed response bound, the same untrusted-dialogue instruction and the same validated JSON schema. GPT-OSS requests use low reasoning effort. Existing consent, batch, redaction, training confirmation and private-feed checks still apply. Only safe provider labels are saved as private provenance. No provider names are added to the website. Kaggle V6 already consumes the provider-neutral feed; it needs no restart or new keys for this change. Deploy the updated API and configure the Groq key to activate it. No new provider calls were made during local verification.

Three consecutive rejected rounds pause after the last confirmed backup and refuse automatic restart until the reports are investigated. Missing improvement is not hidden by resetting a rejection counter.

Session defaults remain up to twenty rounds/eight hours and 96 teacher calls. Intermediate checkpoints are local until `checkpointBackupConfirmed: true`; public model publishing stays manual. Full working checkpoints are about 1.2 GB and remote version history can still grow substantially. Verified temporary downloads avoid accumulating old complete model files in the local Hub download cache. A real capacity probe runs on the selected GPU configuration before initialization. Local tests establish curriculum exclusions, turn-weighted gradients, early-candidate retention, optimizer resume, two-worker equivalence, explicit pause behavior and atomic shard downloads; they do not establish improved conversational quality on the actual trained V10 model. That requires Kaggle's evaluations and reply inspection.

## V11: corrected grading and safe checkpoint selection

Use `model/Nebula_Kaggle_V11_Verified.ipynb`, also copied to `kaggle-transfer`. Stop V10 after a confirmed backup, import V11 into a private Kaggle notebook, enable Internet and T4 x2, enable the same secrets, and Run all. This is a research notebook update; no website/API deployment is required. All older runs remain intact. New snapshots use only `experiments/nebula-v11-verified`, and publishing to public users remains disabled.

V10's diagnostic pass flags were too permissive: a keyword could pass even in an incoherent reply. Its readability and low-loss scores did not establish correct answers. V11 re-grades the saved V10 baseline, best, working and latest checkpoints under the same new versioned protocol before selecting a starting point. Old scores are never used as the new baseline. Compatible accepted optimizer state, training data, fixed validation bytes, licenses and the protected anchor are preserved. The owned 100M network and 80/20 conversation/mixed curriculum remain, including equal assistant-turn weighting, historical replay and checked teacher practice.

Exact tasks now check complete answers rather than words embedded in unrelated text. Wrong explicit additions cannot pass by ending with the right number, copying requires exact text, and restricted identity/name/extraction checks distinguish the roles in the answer. Copying and name/context counts are reported separately. Other replies need semantic review for relevance, coherence, correctness and following the request. Approval requires two successful review calls; a negative rubric criterion rejects the reply. AI review is fallible and is labeled `humanVerified: false`. Readability remains a distinct metric.

The evaluator uses optional `NEBULA_JUDGE_GROQ_KEY`, otherwise the existing separate `NEBULA_TEACHER_GROQ_KEY`; it never uses production review credentials. Only synthetic evaluation conversations and generated test replies are sent to the evaluator. They are never added to training data or sent to the dialogue generator. The two review calls default to the same model and may share biases. `NEBULA_JUDGE_GROQ_MODEL` and `NEBULA_JUDGE_CONFIRM_MODEL` are part of the protocol; changing them on an existing run is blocked rather than comparing mixed grading systems.

Missing keys, malformed verdicts, timeouts, incomplete confirmations and rate limits leave answers pending, never passed. Valid judgments are cached by protocol/question/answer. Review is bounded to sixteen calls per checkpoint and consumes separate quota from the dialogue-generation budget. A partially reviewed round backs up all candidate checkpoints, including available optimizer state, and stops. Run all later retries those candidates before training more; it does not count an API outage as a rejected training round. Initial re-grading must also finish before training starts. A rejected trial retains the last accepted working optimizer rather than silently resetting it. Three fully reviewed rejected rounds pause the experiment for inspection.

Full candidate backups can require several GB, and private repository history grows. Wait for `checkpointBackupConfirmed: true`. Reports include full generated answers, local check methods, rubric votes, pending counts and reasons. V11 scores can be lower because false positives were removed; this does not mean the saved weights were erased. The bounded live reviewer smoke test rejected the three reported bad answers and accepted three clear correct controls using two calls; this small test does not establish broad evaluator accuracy or improved trained-model competence.

## Nebula Cloud

Nebula Cloud is Ultra's account-owned tool workspace and background task system.
Weather is one tool, not the purpose of the feature. No browser extension is needed.
The UI has immediate tool controls and a general task builder.

### Tools available to Ultra

- `search_web`: search current web information through Brave, with source links.
- `read_webpage`: retrieve text from a public HTTPS page. DNS must resolve to
  public IPv4; the approved address is pinned to the TLS connection. Private,
  loopback and metadata networks, credentials, custom ports, redirects,
  non-text content and oversized responses are rejected. No cookies, login or
  page JavaScript. Dual-stack sites can use their approved public IPv4 address.
- `get_weather`: current model-based conditions; ambiguous places require a
  city, region and country rather than silently picking the first match.
- `calculate`: arithmetic with numbers, parentheses and + - * /. No eval/code.
- `list_cloud_tasks`: list only the authenticated account's task statuses.
- `propose_cloud_task`: produce a draft for review. This never creates a task,
  sends email, or changes a connected account by itself.

The chat tool loop permits at most three read-tool calls and four model calls,
with per-request timeouts and a bounded loop deadline. Search/page text is
untrusted data, not instructions. Sources appear in Cloud workspace. Tool
failures are reported rather than replaced with invented results. Guests must
sign in for connected cloud tools. No arbitrary website login, file execution,
purchases or unrestricted cloud desktop is implemented.

### Future tasks

| Task | Input | Result |
| --- | --- | --- |
| Reminder | Reminder text | Save or email that text at the chosen time |
| Write, explain or plan | A content-generation request | Generate text using Ultra; no code execution or interface actions |
| Web research | A search query up to 300 characters | Collect fresh search excerpts with source URLs at execution time |
| Weather check | City, region, country | Fetch conditions when the task runs |

All four can save results in **Nebula Cloud** without Gmail. Email delivery
requires a connected Google account and is a separate explicit choice. The
confirmation shows the task, destination, sender/recipient when applicable,
absolute date/time and time zone. Results can be viewed in the task list.
Tasks run once between one minute and seven days ahead. No chat history is
included in task execution. Ordinary content generation does not create or
modify files on external sites.

### Server configuration

Existing Ultra, Firebase and rate-limit variables still apply.

| Variable | Value/source |
| --- | --- |
| `NEBULA_SEARCH_API_KEY` | Brave Search API key; only search/research require it |
| `NEBULA_CLOUD_ENABLED` | `true` after configuring the delayed queue |
| `QSTASH_TOKEN` | Upstash QStash API token |
| `NEBULA_SCHEDULE_WORKER_SECRET` | Independent random secret, at least 32 characters |
| `NEBULA_QSTASH_URL` | Optional region endpoint; default `https://qstash.upstash.io` |
| `NEBULA_PUBLIC_API_URL` | `https://api.scriptnovaa.com` |
| `NEBULA_PUBLIC_SITE_URL` | `https://scriptnovaa.com` |
| `NEBULA_GOOGLE_CLIENT_ID` | Google OAuth Web application client ID; email only |
| `NEBULA_GOOGLE_CLIENT_SECRET` | That web client's secret; email only |
| `NEBULA_CONNECTION_ENCRYPTION_KEY` | 32 random bytes encoded as base64; email only |

`NEBULA_SCHEDULE_ENABLED` remains a compatibility fallback when
`NEBULA_CLOUD_ENABLED` is absent. Workspace tasks need the queue but do not need
Google credentials. Scheduled writing also needs the existing Ultra model key.
No third-party account or paid plan was provisioned by this code update.

For Gmail, enable Gmail API and configure a Web OAuth client with this exact
redirect URI: `https://api.scriptnovaa.com/api/nebula/cloud/google/callback`.
Consent requests `openid`, `email`, and `https://www.googleapis.com/auth/gmail.send`
with offline access and PKCE. It does not request inbox-reading permission.
Google may require test users or public app verification. This connection is
separate from Firebase website sign-in. Users authorize on Google's own page;
Nebula never receives their Google password.

Generate the encryption value with Node's `randomBytes(32).toString('base64')`;
generate the worker secret independently. Keep both server-side. Tokens are
AES-256-GCM encrypted in Realtime Database paths denied to direct clients.
Retain the encryption key across deployments; changing it requires reconnecting
Google. OAuth state is single-use, expires after ten minutes, and is bounded
to one active authorization per account. No tokens enter model prompts,
training examples, browser responses, or application logs.

QStash receives an opaque account key and task ID, not Google credentials or
chat history. Its delayed callback goes to `/api/nebula/cloud/dispatch` with
the separate worker bearer secret. No page timers or Vercel Hobby cron are
needed. Queue availability/plan limits still apply; exact-second delivery is
not guaranteed. Search requires its API key. The public Open-Meteo endpoint
is for noncommercial use; commercial deployment needs an appropriate service
plan/integration and attribution.

### Task integrity

Creation uses an idempotency key, and workers claim stored leases. Repeated
callbacks, cancelled tasks and cross-account access cannot produce duplicate
sends. Email jobs bind the chosen Google connection; disconnecting or changing
it prevents pending jobs from using a different sender. A persisted `sending`
boundary precedes Gmail. If delivery cannot be confirmed, the task is marked
**needs attention**, never automatically resent. Check Gmail Sent before
creating a replacement; Gmail and our database cannot form a single
exactly-once transaction. In-progress sends cannot be cancelled retroactively.
Jobs over an hour late fail. Stale worker leases surface when the user opens
the workspace. The task store retains at most 20 active and roughly 50 total
jobs per account. Results and task instructions are separate from chat
training sharing.

Endpoints under `/api/nebula/cloud`: `GET /`, `POST /search`, `POST /read`,
`POST /calculate`, `POST /weather`, `POST /google/connect`, `GET /google/callback`,
`DELETE /google`, `POST /jobs`, `DELETE /jobs/:id`, and protected `POST /dispatch`.
The original weather-email payload remains accepted for older clients.
