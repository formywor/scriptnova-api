# Nebula API

Server-only source for the existing Vercel project. Upload the contents of this `api` directory to the API repository root. The main website remains a separate GitHub Pages repository. No secrets belong in either repository.

## Public experimental model

`model-assets/release.json` pins V4 trial 1: 8,227,328 parameters, 35/70 limited diagnostics. The exported weights are split into six `model-assets/nebula-v4-experimental-1-*.part` files, each at most 8 MiB, and verified by size and SHA-256 after assembly. Upload all six parts and `release.json`. They stay on the API server. This model is experimental and frequently gives incorrect or unclear answers, including basic arithmetic. The website says so. Passing these checks is not general chat readiness.

Node 24 runs the owned Transformer directly with per-request KV caching. No teacher API or external model host is needed in embedded mode. Set `NEBULA_MODEL_MODE=embedded` to select it; an unset mode also uses embedded inference when no external model URL is configured. Existing external mode is supported via server-only `NEBULA_MODEL_URL` and `NEBULA_MODEL_KEY`. No model configuration is offered to visitors.

The model supports at most 1,024 bytes/tokens of instructions and context and replies with at most 96 generated bytes. Complete owner instructions and the latest question are preserved; older context may be omitted. Oversized latest messages return `MODEL_CONTEXT_LIMIT` without charging a successful answer. Inference has a 65-second deadline. Local PyTorch/Node export comparison measured a maximum logit difference below 0.00002; one identity check and parity prefill took about six seconds combined on the local machine. Vercel performance and free usage quotas can differ.

The Vercel configuration explicitly bundles the release and model asset, routes requests to root `index.js`, and sets a 120-second function duration. `model/` is excluded from the deployment. Keep `lib`, `scripts`, `nebula-rules.json`, package files and model assets together. Run `npm install` and `npm run check`. Local preparation is not proof of a successful Vercel deployment.

## Accounts, storage, and contributions

Keep the existing Firebase server credentials, public Firebase app configuration, allowed origins, and stable random `NEBULA_RATE_LIMIT_SECRET` in Vercel. The rate-limit secret needs at least 32 characters. Firebase verifies ID tokens server-side. Account chats and preferences sync through the API; guest chats are temporary and have a shared-network question allowance. The supplied database rules deny browser database access. CORS is not authentication.

Sharing is on for new accounts and can be disabled in Settings. The server requires the account sharing preference, new-turn eligibility flag, versioned contribution flag, valid identifiers, and a fresh consent-generation check after generation. Set `NEBULA_TRAINING_ENABLED=false` to disable capture globally; otherwise consent-controlled capture is enabled. Imported older messages are excluded.

Only the latest consented message and reply become pending review records in private Firebase `nebulaTraining/v1`. Basic email/key redaction is not a comprehensive personal-data filter. Raw messages are not application logs. Public submissions and the model's own replies are never automatically accepted as factual teaching answers.

Captured account turns also produce a small private `nebulaLearning/v1` metadata index containing a topic, timestamp, and consent ownership references, with no chat text. The trainer-only `GET /api/nebula/research/curriculum` samples at most 100 owners, rechecks current account sharing and generation, uses the last seven days, and returns only four coarse topic counts rounded to multiples of five. It never returns text, IDs, names or replies. The sample rotates hourly. The evaluator token and browser-origin requests cannot read this feed.

The V5 GPU worker actually uses these counts to choose verified practice for at most one round in four. This influences weight updates through owned exercises; it does not instantly memorize a visitor's messages or train on unchecked answers. Small samples or an unavailable API feed fall back to the normal curriculum. Raw contributions remain pending for separate operator review. Account opt-outs exclude existing contributions from future topic requests. Deleting shared data tombstones both contribution stores and rotates the account generation. Deletion cannot undo completed training. Chat deletion and shared-data deletion are separate controls.

## V5 ongoing private training

Use `model/Nebula_Kaggle_V5.ipynb` in a private Kaggle notebook with Internet enabled and GPU T4 x2 when available. Stop duplicate/older workers. Enable existing Kaggle secrets `NEBULA_TRAINER_TOKEN` and `NEBULA_HF_TOKEN`. The API requires `NEBULA_RESEARCH_ENABLED=true` and distinct trainer/evaluator secrets. The private repository is `iiidevv/nebula-research`; tokens remain platform secrets.

V5 starts from the strongest saved V4 checkpoint at a pinned revision, not the original untrained growth model or latest rejected trial. It preserves V4 and the older API campaign. The dataset has 32,103 rows, with 5,590 new original short conversations, follow-ups and exact arithmetic examples. Existing public/teacher provenance and licenses are retained. Whole held-out V4 scenarios remain excluded; familiar 2+2 is explicitly rehearsed and is not an unseen test.

The notebook benchmarks one versus two GPUs, trains in 500-update rounds, saves locally every 100 updates, and evaluates final and lowest-loss checkpoints. It checks the same V4 validation sample, frozen task diagnostics and six additional conversation checks. A broader-gain research rule permits modest category tradeoffs while rejecting large health/loss deterioration. Each round changes its deterministic sampling seed, so rejected trials do not endlessly replay identical batches. After rejections it rotates focus and reduces learning rate rather than automatically stopping at three. Rejected trials never overwrite the selected best model.

Each completed round atomically commits weights, reports and the resume manifest to `experiments/nebula-v5/` in private Hugging Face, guarded by parent revision and checked on download. Latest and best weights are separate. Remote snapshots omit optimizer state, so resumed rounds intentionally start fresh AdamW. A failed backup stops the run. An abrupt disconnect can lose work since the last confirmed remote backup.

Each session runs for at most eight hours or 100 round backups. Run the same notebook with the same run name to continue uploaded progress. Platform GPU/session quotas still apply. Repository history consumes storage: about 3.3 GB for 100 latest snapshots, plus best snapshots. Monitor repository storage. Use the notebook stop button or create `STOP_AFTER_ROUND` in the project directory for a graceful stop after the current backup.

Training never changes the public release automatically. To release a later checkpoint deliberately, export it with `model/export_node.py`, package that export with `model/package_node_release.py`, update the model part names in `vercel.json` includeFiles, inspect replies, and deploy the API. The original coordinated trainer/evaluator and V4 notebooks are retained for research history; their three-rejection pauses remain unchanged. V5 is a separate experiment.


## Conversation experience and optional reviews

GET `/api/nebula/models` returns the fixed owned-model choices and feature availability, never private provider configuration. Clients select only allowlisted model IDs and Quick/Standard/Expanded generation budgets. Extended reasoning is explicitly unavailable. Account personalization, starter-question preferences, display settings and default model/length choices are validated and synchronized through account preferences. Owner instructions remain first; preferences are subordinate context, not a replacement for server rules.

Optional external answer review requires three private Vercel variables: `NEBULA_REVIEW_ENABLED=true`, `NEBULA_REVIEW_API_KEY`, and `NEBULA_REVIEW_MODEL` (a model available to that key). The current server adapter uses the Gemini generateContent API. The existing server-side `GEMINI_API_KEY` can be used as a key fallback. No provider key or model endpoint goes in website files. Deploy both API and website updates.

The public setting is **Allow third-party AI reviews**, directly below **Improve Nebula for everyone**. New accounts start with both settings on, disclosed in sign-in and settings. Either can be changed independently. Turning training sharing on enables reviews only if the user has never manually set a review preference. Existing manual opt-outs are retained. Existing accounts without explicit review consent remain off until enabled.

Reviews include the whole eligible conversation, redacted, excluding exchanges sent with review off, Classic, imported/unversioned answers and prior published checkpoint revisions. New server answers carry a checkpoint fingerprint and timestamp. About three fresh replies trigger a batch; rapid chats (five replies within five minutes) wait for eight fresh replies or ten idle minutes. Other chats flush after five idle minutes. The open website scans saved chats once a minute, including chats not currently open; checks resume on return. There is no closed-browser background scheduler. Server leases prevent duplicate calls across devices. A one-minute account cooldown, five-minute chat cooldown and ten-minute failure retry replace the old three-attempts/48-hour cap; provider failures defer quietly. Reviews over 120,000 serialized characters are skipped rather than silently truncated. Remote models should set NEBULA_MODEL_REVISION to a new identifier whenever their deployed weights change.

The provider sees dialogue only, never account profiles, memory or credentials. It reviews the dialogue as context and proposes a correction for the final answer. Results are attached to a pending contribution only when training sharing is also on and the contribution remains eligible. Review-only mode does not export training data. Opt-outs are checked before the call and before persistence; a call already sent cannot be recalled.

Reviews are stored privately alongside pending contributions. The private `model-data.mjs export` command includes proposed corrected answers and review provenance, but keeps every row pending for operator approval. Uncertain reviews do not replace the original answer. The existing consent-checked review/training pipeline can then use approved corrections. Neither public model weights nor Kaggle V5's fixed research dataset change automatically from these reviews. The V5 notebook still uses anonymous topic-guided verified practice. No automatic public promotion is added.

## V6 conversation training and checked review corrections

Use `model/Nebula_Kaggle_V6.ipynb` (also copied to `kaggle-transfer`). Stop older trainer sessions after a confirmed backup. V6 initializes from the current best V5 weights in private Hugging Face, retains their step count, and writes a separate `experiments/nebula-v6` run. Missing V5 progress is an error, not a silent restart. The V5 files remain intact. Re-running V6 resumes its saved best model.

Four of every five optimizer updates use conversation batches. One of five uses mixed practice; alternating mixed batches explicitly practice memory. This is an update ratio rather than an exact token ratio. The dataset adds 608 owned multi-turn dialogues on follow-ups, changed context, writing revisions, plans, explanations and stories. Grouped splits and original frozen task exclusions remain. Evaluation runs each 500 updates; V6 permits small overall-score tradeoffs for actual conversation gains while protecting memory, extraction, identity, arithmetic and readability.

New review results may also provide training examples. The first pass rewrites the final question into a self-contained question and proposes an answer. A separate call must judge that pair acceptable. Owner rules, length checks, contact/credential-marker filters, personal-memory exclusion and a simple arithmetic check also apply. Two passes of the same AI are not independent proof of correctness. Uncertain, conflicting or malformed results remain excluded from automated training. Temporary second-pass failures retry later. Review-only accounts produce no training examples.

The checked pair is indexed privately in `nebulaReviewTraining/v1`, never application logs or public routes. Trainer-only GET `/api/nebula/research/review-training` requires the trainer token, rejects browser origins/evaluator tokens, and rechecks both account toggles and current generation. The service-wide training switch also applies. It returns at most 64 self-contained, filtered pairs without account IDs. Shared-data deletion tombstones the index. Withdrawal prevents future reads; it cannot undo completed updates or cancel an already-running round.

V6 fetches a fresh feed every round, clearing the prior round's file first. An unavailable API or an empty feed means no review examples; owned/public practice continues. Frozen probes are excluded again locally. At most one in ten conversation updates uses these corrections (at most 8% of all updates). Logs show `checkedReviewExamples`, `reviewedTrainingWindows` and actual `reviewUpdates`; only a positive `reviewUpdates` confirms reviewed examples were used in weight updates. Feed text lives in a temporary directory outside Kaggle working outputs, is cleaned up after the training subprocess exits, and is not included in remote dataset snapshots. Review-derived weights can retain learned information, which is why both sharing settings are required.

The older manual export remains pending for operator approval; V5 notebooks do not consume this new feed. Deploy the API and website and import the new V6 notebook for this path to operate. No new secret values are needed. Research training still never automatically replaces the public website model.

## Review provider routing

Reviews can use Groq and Gemini. Add `GROQ_API_KEY` (or the dedicated `NEBULA_REVIEW_GROQ_API_KEY`) in Vercel; `NEBULA_REVIEW_GROQ_MODEL` defaults to `openai/gpt-oss-20b`. Existing `NEBULA_REVIEW_API_KEY`/`GEMINI_API_KEY` and `NEBULA_REVIEW_MODEL` remain Gemini's configuration. Either provider alone is sufficient. `NEBULA_REVIEW_ENABLED=true` still gates all reviews. Keys and model configuration remain server-only.

First passes alternate between configured, healthy providers using a Firebase transaction. Confirmation prefers the other provider when healthy, with fallback to the working one. Valid uncertain/rejected verdicts are not failures and never trigger a search for an approving provider. HTTP errors, rate limits, timeouts and malformed output try the other provider immediately. Failures create a shared 1-minute cooldown, increasing up to 15 minutes for repeated failures; when it expires the provider becomes eligible for a probe. If only one is healthy, all new calls go there. If both are unavailable, reviews defer; ordinary chat continues. The cooldown survives Vercel cold starts through `nebulaReviewRouting/v1`.

Both transports use fixed HTTPS hosts, no redirects, 18-second request timeouts, a 24 KB streamed response bound, the same untrusted-dialogue instruction and the same validated JSON schema. GPT-OSS requests use low reasoning effort. Existing consent, batch, redaction, training confirmation and private-feed checks still apply. Only safe provider labels are saved as private provenance. No provider names are added to the website. Kaggle V6 already consumes the provider-neutral feed; it needs no restart or new keys for this change. Deploy the updated API and configure the Groq key to activate it. No new provider calls were made during local verification.
